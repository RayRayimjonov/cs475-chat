# Evidence collected 2026-11-12

Facts only, reproducible from the commands named.

## Correction to an earlier reading

An earlier pass concluded "zero remote machines" from `server.py`'s log. That was the
wrong layer. `webchat.py` opens the TCP connection to the chat server on behalf of a
browser, so **every** browser user appears to the chat server as `127.0.0.1`,
whatever device the browser is on. Client origin for browser users is visible only on
the gateway's port (8080).

## What this settles

1. **Campus Wi-Fi does not isolate clients.** Devices on `10.10.0.x`, `10.128.14.x`
   and `10.128.15.x` all reached the server on `10.128.15.155:8080`. The feared cause
   in Problem A is ruled out for this path.
2. Several machines use the system simultaneously, including a mobile device.
3. The server's bind and the firewall rules are correct, as previously verified.

## What is still not established

4. **No remote `client.py` has connected.** Every connection on port 5050 came from
   `127.0.0.1`, meaning the raw TCP client has still only been exercised on one
   machine. Browser users reach 5050 through the gateway, which is local.

   Closing this needs one command on another laptop:

       python client.py --host 10.128.15.155 --nick aden

   After that, `Connection from 10.128.x.y` appears in the server's own log with an
   address that is not this machine, and the raw TCP path is proven cross-machine too.
